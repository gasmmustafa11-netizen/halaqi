1. ROOT CAUSES IDENTIFIED

ROOT CAUSE 1 (Critical) — Users never loaded to memory on Vercel
----------------------------------------------------------------------
File:    src/server/db.ts:4779 (loadAllFromNeon)
Impact:  Likes appear broken in feed on Vercel

loadAllFromNeon() loads 14 tables into db.getState() but omits the users
table. The function loadUsersFromNeon() exists at line 4747 but is never
called from loadAllFromNeon() or from ensureNeonDataLoaded() in app.ts.

On Vercel, ensureNeonDataLoaded() calls loadAllFromNeon() per cold start,
so db.getState().users is ALWAYS empty. This causes optionalAuthMiddleware
(which calls db.getUserById() against in-memory users) to silently fail
for every request, setting req.user = undefined even for authenticated users.

The /api/posts/feed endpoint uses optionalAuthMiddleware (global), NOT
requireAuth. So req.user?.id is always undefined, viewerUserId is always
empty string, and the SQL check pl.user_id = '' never matches. Result:
liked_by_me is FALSE for ALL posts regardless of actual like state.


ROOT CAUSE 2 (Major) — Salon post like notifications never fire
----------------------------------------------------------------------
File:    src/server/db.ts:3614-3655 (togglePostLike, salon branch)
Impact:  Salon post owners are never notified when someone likes their post

The salon post branch of togglePostLike only selects 'id' from salon_posts
in its post_check CTE (line 3615-3619). The final SELECT returns
NULL AS post_owner_id (line 3650).

The notification condition at line 3666-3682 requires BOTH:
  - postType === 'user' (explicitly blocks salon posts)
  - toggleRow.post_owner_id to be truthy (is NULL for salon posts)

Since both conditions fail for salon posts, no notification is ever created.


ROOT CAUSE 3 (Moderate) — Comment notifications use wrong type
----------------------------------------------------------------------
File:    src/server/db.ts:3900
Impact:  Comment notifications are indistinguishable from system notifications

Comment notifications are created with type: 'system' instead of a distinct
'post_comment' type. The Notification type in types/index.ts does not even
include 'post_comment' as a valid union member.


ROOT CAUSE 4 (Moderate) — optionalAuthMiddleware has no Neon fallback
----------------------------------------------------------------------
File:    src/server/authMiddleware.ts:76-94
Impact:  Even with valid token, optional auth silently drops user context

optionalAuthMiddleware only checks in-memory state via db.getUserById().
Unlike requireAuth (which queries Neon directly via getUserByIdFromNeon),
optionalAuthMiddleware has no fallback. On Vercel where users are never
loaded to memory, this always fails silently.

4. EXPRESS 4.22.2 AND ASYNC MIDDLEWARE SAFETY
================================================================================

Express version: 4.22.2

Fix 4 changes optionalAuthMiddleware from sync to async. Analysis:

- Express 4.x does NOT natively handle async middleware errors. If an
  async middleware throws an unhandled rejection, Express will NOT catch
  it — the request hangs or crashes.

- HOWEVER, the new optionalAuthMiddleware wraps its async Neon call in
  try/catch with an empty catch block:
    try { user = await db.getUserByIdFromNeon(payload.userId); ... }
    catch { /* proceed without user context */ }

- The catch block means no unhandled rejection can escape. The middleware
  ALWAYS calls next(), whether the Neon query succeeds, fails, or the
  user is not found. The request always continues.

- This is the same pattern already used by requireAuth (line 97-174 in
  authMiddleware.ts), which is also async and wraps its Neon call in
  try/catch.

- Express 5.x (not used here) would handle async rejections natively,
  but the explicit try/catch makes this safe on Express 4.x.

Conclusion: The async middleware is safe on Express 4.22.2 because:
  1. All paths call next()
  2. The async Neon query is fully wrapped in try/catch
  3. The pattern matches existing code (requireAuth)

7. REMAINING CONCERNS
================================================================================

7a. No automated tests
    The project has no test framework. All verification is manual via
    tsc and vite build. Functional testing (actual Like/Comment/Notification
    behavior) must be done manually in browser after deployment.

7b. Express 4 async middleware
    While safe due to try/catch, Express 4 does not propagate async
    errors. If future changes remove the try/catch, unhandled rejections
    would silently break. A comment in the code warns about this.

7c. Notification type backward compatibility
    Existing notifications in Neon with type='system' will remain as
    'system'. Only new comment notifications get 'post_comment'. If the
    frontend needs to distinguish them, a one-time migration or filter
    logic would be needed.

7d. Neon cold start latency
    Fix 4 adds a potential Neon query to optionalAuthMiddleware if the
    user is not in memory. On Vercel cold start, this adds ~50-200ms
    latency to the first request per user per instance. Subsequent
    requests on the same instance use in-memory cache.

7e. User cache staleness
    optionalAuthMiddleware caches Neon users back into db.getState().users.
    If a user changes their name, role, or ban status, the in-memory
    cache becomes stale until the next cold start. This is a pre-existing
    pattern (requireAuth already has the same behavior at line 127-134).

7f. loadUsersFromNeon() is called LAST in loadAllFromNeon()
    If any earlier table query fails (e.g., salons), the entire
    loadAllFromNeon catches and logs the error, but loadUsersFromNeon
    at the end may not be reached. However, the Neon initialization
    in app.ts uses a Promise that resets on failure, so the next
    request will retry.
